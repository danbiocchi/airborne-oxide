# ADR-0004: Parameters and scenario files

**Status:** Accepted (M1c part two) · **Date:** 2026-11-11 · **Design reference:** DESIGN §4.14, §5.5

## Context

DESIGN §4.14 asks for parameters declared once, editable at run time, stored safely, and logged on change. DESIGN §5.5 asks for scenarios as TOML files that CI flies across many seeds.

Today the flight core has 100 tunable values in five structs (`Gains`, `Limits`, `EkfParams`, `FailsafeParams`, and the vehicle description). Their defaults live in `Default` impls, 39 of them have no range check, and nothing can change one after `Core::new`. The simulator's 43 scenarios are Rust code: 20 named failures, 21 pairings generated by loops, `hover-step` and `gust-hold`.

Part one's trace hashes are the safety net for this work. Moving a value from code to a table or a file must not change one bit of any flight.

## Decision

### 1. One table, declared once

`oxide-core::params` declares every parameter exactly once: its name, type, default, minimum, maximum, unit, group, description, and which configuration field it is. A declarative macro (no new dependency) turns the declarations into:

- `PARAMS`, a static table of `ParamDef` (metadata only, no allocation);
- `ParamId`, the index into it;
- `get(cfg, id)` and `set(cfg, id, value)`, which read and write the configuration field.

**The configuration structs stay the storage.** The control loops keep reading `cfg.gains.rate_p.x` as today, at no cost. There is no second copy to keep in step.

**Defaults come from the table.** The `Default` impls of `Gains`, `Limits`, `EkfParams`, `EstimatorConfig` and `FailsafeParams` are built from the table's defaults. A test pins every default to its value before this change, bit for bit.

**Names** are at most 16 characters of `A–Z`, `0–9` and `_`, so they fit MAVLink's parameter protocol unchanged. They are ours, not ArduPilot's or PX4's. A prefix gives the group: `RATE_`, `ATT_`, `POS_`, `LIM_`, `EKF_`, `FS_`, `BAT_`, `RTL_`, `LAND_`.

**Types** are `f32` and `i32`, the two MAVLink carries without loss.

**Units are the core's own:** radians, metres, seconds, volts. One conversion exists: the fields held as whole microseconds are parameters in seconds, rounded to the microsecond. A ground station may show degrees; the table says `rad`.

### 2. What is a parameter

| Group | Count | Parameter? |
|---|---|---|
| Gains, limits | 39 | Yes |
| Estimator noise, gates, timeouts | 25 | Yes |
| Failsafe thresholds, delays, speeds | 27 | Yes |
| Estimator source (EKF or external) | 1 | Yes, changeable only while disarmed |
| Vehicle description: mass, inertia, rotors, thrust curve, battery cells, resistance, nominal voltage | 8 + rotors | **No.** It stays in the airframe file |
| Internal constants (buffer sizes, the stillness test, RTL arrival tolerances, switch confirmations) | 37 | No, except the stick deadband |

The vehicle description is structural: the rotor count is a compile-time size, and a change rebuilds the mixer. It changes when the hardware changes. Making it parameters belongs with the airframe lab (DESIGN §6).

### 3. Every parameter has a range, and the whole must hold together

- **Per parameter:** `set` refuses a value that is not finite or is outside `[min, max]`. The 39 gains and limits that had no check get ranges now.
- **Together:** after a change the configuration must still pass `validate` (critical battery not above low, landing speed at least twice the touchdown speed, and the rest of ADR-0003 §6). A change that would break it is refused, and the configuration is left as it was.
- **A refusal says why:** unknown parameter, wrong type, out of range, breaks a rule, or not while armed.

### 4. Changing a parameter at run time

A change arrives through the core's inputs, like every other command: `Inputs.param_set`, at most one per tick. The supervisor applies it, so a change is deterministic and replayable from a log.

- **`ParamChanged` and `ParamRefused` events** report the outcome. That is the "every change is logged" of DESIGN §4.14.
- **Live or disarmed-only.** Gains, limits and failsafe values take effect on the next run of the task that reads them, in flight too. Parameters whose change rebuilds something (the gyro filter cut-off, every estimator parameter, the estimator source) are refused while armed.
- **Unsaved changes** are flagged in the status until the store has them (§6).

### 5. Parameters in files

A `[params]` table of `NAME = value` is accepted in three places, applied in this order, each through the same checked `set`:

1. the airframe file (tuning that belongs to the airframe);
2. the scenario file;
3. the command line (`--param NAME=VALUE`, `--params FILE.toml`).

`oxide-sim params list` prints the table, `params json` writes the metadata file QGroundControl reads, and `params doc` writes `docs/PARAMETERS.md`. CI regenerates the last and fails if it differs from the file in the repository.

### 6. Storage

`oxide-store` is a small `no_std` crate: a log-structured store over two flash sectors, behind a `Flash` trait with NOR semantics (program clears bits, erase sets a sector).

- **Records** are fixed-size: a 32-bit key (a hash of the parameter name, so reordering the table never changes a meaning), the value's 32 bits, and a CRC. A torn record fails its CRC and is skipped.
- **Compaction** copies the newest value of each key to the other sector, marks it valid, and only then is the old sector erasable. Power loss at any point leaves one valid sector.
- **Wear** is the erase count, kept in the sector header and reported.
- **Tested on the host** against a simulated flash that cuts the power after every single byte of every operation: after each cut the store must return, for every key, either the old or the new value, never anything else, and never lose an acknowledged write.
- **Never while armed.** The core hands out unsaved changes only while disarmed. The firmware writes them then.
- **A corrupt or unreadable store** loads defaults, sets the `CONFIG` pre-arm bit, and arming stays refused until an operator acknowledges it (`Inputs.param_ack`).
- A value on flash that is out of range for the running firmware is dropped for its default and reported the same way.

The simulator keeps parameters in TOML files; `oxide-store` is exercised by its own tests and wired to real flash at F405 bring-up.

### 7. Scenario files

One TOML file per scenario in `scenarios/`. A file holds:

| Table | Content |
|---|---|
| top level | `name` (also the random-seed key), `about`, `airframe`, `duration_s` |
| `[sim]` | sensors (`ideal` or `realistic`), estimator source, links and heartbeats |
| `[wind]` | calm, steady, or the randomised gust generator with its ranges |
| `[battery]` | capacity and starting charge, when the scenario overrides the airframe |
| `[params]` | parameter overrides by name |
| `[[fault]]` | kind, start, end |
| `[pilot]` | arming time, and timelines of mode switch, sticks, kill switch and setpoints |
| `[expect]` | states and reasons that must or must never appear, the ending, limits |
| `[run]` | seeds and profiles for the Monte-Carlo job |

- **Unknown keys are errors.** A typo must not become a default.
- **Names, not numbers,** for states, reasons, actions and modes.
- **Heights are up-positive in files;** the loader converts to NED.
- **Concrete numbers only.** The 21 pairings become 21 files. Battery sizes that were computed from a target time are written out. A test checks that every pairing of the seven failure kinds has a file, so coverage cannot quietly shrink.
- **Rotor count:** four, until another airframe exists.

**The files replace the Rust definitions, and the proof is the hashes.** First every scenario is exported from Rust to TOML and loaded back; the trace hash from the file must equal the hash from the Rust definition, for every scenario, on index 0 and one other. Then the Rust definitions are deleted.

`oxide-sim scenario` takes a name or a path. `oxide-sim scenarios DIR --seeds N` flies every file on both profiles and prints one line each; CI's Monte-Carlo job runs that.

`hover-step` keeps its M1a requirements as Rust tests (they check positions at set times, which `[expect]` does not express); the file carries its flight.

## Consequences

- A value has one home. Docs, ground-station metadata and defaults are all generated from it.
- A parameter change in flight is an input, so a replay reproduces it.
- Adding a scenario is adding a file; no Rust.
- The parameter table costs about 3 KB of flash for metadata and no RAM beyond the configuration that already exists.

## Deferred

- The MAVLink parameter protocol itself (with communications).
- Vehicle description as parameters (with the airframe lab).
- Parameter groups that must change together in one step (a transaction). Until then, change them in an order that keeps the configuration valid.
- Per-parameter access levels for the brain (with the command gateway, M3).
- The flash driver and the erase stall on the F405 (bring-up).
- Terrain and missions in scenario files (they do not exist yet).
